| 2026-10-03 | React Testing Library in Vitest Requires Explicit `afterEach(cleanup)` to Prevent DOM Accumulation | When testing multiple complex components or full App integration in a single Vitest test file, previous rendered trees persist in `document.body` if not explicitly cleared after each test, leading to unexpected `Found multiple elements with...` errors on common UI text | Always configure `afterEach(() => cleanup())` in `setupTests.js` and use precise role/aria queries to verify UI states predictably across regression runs. |
| 2026-10-03 | Multi-Layer Navigation & Banner Duplication Degrades Information Scent | When designing a high-density single-page or canvas-based application, repeating navigation elements (e.g. 7 tabs at the top of the canvas AND 7 buttons at the bottom) or stacking redundant section banners below the sheet title dilutes the user's focus and wastes vertical real estate | Use pagination patterns (Prev/Next) for bottom rails instead of mirroring full tab bars, gate standalone headers with `isEmbedded` checks when components are projected into parent sheets, and reserve sticky space for the primary navbar. |
| 2026-10-03 | Button Label Conciseness and Column Sizing Prevent Unwanted Flex Wrapping | When presenting multi-action button groups in constrained flex rows (e.g. 600px middle columns), appending redundant words like "Profile" to brand icons (e.g. "LinkedIn Profile", "GitHub Profile") pushes total row width past available space, forcing single buttons onto an orphaned second line | Use clean, concise labels ("LinkedIn", "GitHub", "Download Resume"), define all color variants (e.g. `.btn-outline-purple`), and balance 3-column grid tracks (180px - 1fr - 310px) to guarantee single-line alignment without awkward breaks. |
| 2026-10-03 | Vertical Stacking of Equivalent Navigation Sets Creates Visual Ambiguity | Placing two identical 7-item navigation tab bars separated by only ~20px (a command chip bar above, and a window tab bar below) confuses users about where to interact and wastes critical vertical space above the fold. | When an interactive trigger deck already controls a projection viewport, merge the window chrome identity (`● ● ●`, file tag, status indicators) into the command bar itself, and eliminate duplicate secondary tab bars so the viewport immediately displays the selected deliverable content. |
| 2026-10-03 | Stepper Node Text Wrapping Breaks Vertical Centering and Node Proportions | In sequential stepper tracks with connecting arrows, allowing a single node's label to wrap onto multiple lines expands its vertical height unevenly. When the flex container uses `align-items: center`, the taller node protrudes both above and below adjacent nodes, throwing connecting arrows out of alignment. | Always set `align-items: stretch` or a fixed/min-height on stepper cards, apply `white-space: nowrap` on stage labels with sufficient `min-width`, and position connectors using `transform: translate(50%, -50%)` at the exact geometric midpoint between cards. |
| 2026-10-03 | Component Switching from Deep Page Positions Requires Explicit Post-Render Smooth Scrolling | In single-page dynamic sheet applications, clicking deep navigation links in the footer to load dynamic components will switch component state, but if native anchor jumps occur before React renders the pane or if scroll handlers check `scrollY < 200`, the user remains stranded at the bottom of the page. | Couple sheet state dispatchers with an asynchronous post-render `scrollIntoView({ behavior: 'smooth' })` targeting the specific pane or container to ensure the user is immediately redirected right in front of the requested component. |
| 2026-10-03 | Footer Metadata Pruning and Universal Text Centering | Over-populating footers with redundant status badges ("System Online") or split flex layouts creates asymmetrical spacing on wide viewports and awkward wrapping on narrow screens. | A single, centered copyright and professional title block with `justify-content: center` and `text-align: center` delivers a balanced visual termination across all responsive viewports while preventing orphan elements. |
| 2026-10-03 | Small-Screen Overflow Immunity Requires Flex-Wrap and Width Independence | Elements styled with `display: inline-flex` or `white-space: nowrap` (like monospace status badges, dual toggle switches, and floating docks) default to non-wrapping behavior. On devices <= 400px, these single elements frequently exceed the viewport width, forcing the entire page into unwanted horizontal scroll and breaking layout alignment. | Always enforce `max-width: 100%`, `flex-wrap: wrap`, and `word-break: break-word` on long text tags; convert fixed-width toggles into fluid 100% flex rows with `flex: 1 1 0; min-width: 0`; and defensively clamp floating dock widths with `max-width: calc(100vw - 1rem)`. |
| 2026-10-03 | Windows Headless Chrome Window Minimum Width Trap & FontAwesome Free Verification | Running headless Chrome CLI with `--window-size=375,812` on Windows triggers native Win32 window min-width (~500px), producing false cropped captures unless CDP `Emulation.setDeviceMetricsOverride` is used. Furthermore, icons from FontAwesome Pro (like `fa-shield-check`) render as silent blanks under FontAwesome Free CDNs. | Always use CDP device metric overrides with `mobile: true` for mobile regression on Windows, and verify all icon classes against FontAwesome Free catalogs (e.g. `fa-shield-halved`). |
| 2026-10-03 | CSS Media Query Ordering Trap: Broader Queries Lower in the File Override Narrower Ones | Placing an `@media (max-width: 1024px)` block lower in the stylesheet than an earlier `@media (max-width: 768px)` block allows rules in the 1024px query to override the 768px query on mobile due to equal CSS selector specificity and later source order. | Always structure max-width media queries in strictly descending order (1440px -> 1024px -> 768px -> 480px -> 360px), or scope intermediate tiers using range syntax `@media (min-width: 769px) and (max-width: 1024px)`. |
| 2026-10-03 | Floating Action Button Collision on Narrow Mobile Viewports | When multiple fixed elements anchor near the bottom of narrow mobile viewports (e.g. a centered floating dock spanning ~90% screen width and a bottom-right back-to-top button at `bottom: 1.25rem`), they collide and overlap on narrow screens. Furthermore, single-column stacked footers look asymmetrical if left-aligned while copyright and mobile headers are centered. | Elevate secondary floating buttons (Back To Top) to `bottom: 4.5rem` exclusively on narrow mobile viewports (<= 480px) to establish a clean ~20-25px vertical clearance above primary docks, and apply unified center alignment to stacked footer columns on phones. |
| 2026-10-03 | Tablet (768px+) Screen Real Estate Does Not Require Mobile Hardening | Treating 768px tablet viewports as narrow mobile screens causes unnecessary column collapse and excessive vertical stacking. Tablet screens have sufficient width for 2-column or 4-column layouts, and a centered floating dock leaves over 90px of horizontal clearance to corner floating buttons. | Restrict single-column stacking and floating button vertical elevation to phone breakpoints (`max-width: 480px`), allowing tablet screens (768px–1024px) to retain spacious multi-column laptop-style presentation. |
